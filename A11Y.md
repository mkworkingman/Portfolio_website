# Accessibility (a11y)

Reference for keeping this site accessible. Stack context: **vanilla TypeScript + Vite**, a single
`index.html`, styles in SCSS, tests in Vitest + jsdom. No React, no JSX.

---

## 1. Tooling

### Linting — `eslint-plugin-jsx-a11y` does NOT apply here

It only lints JSX elements inside `.jsx` / `.tsx` files. This project has none, so installing it
would be a no-op.

Worth knowing for React work anyway: it is a **static** linter. It catches missing `alt`, `onClick`
on a `<div>` with no keyboard handler, invalid `role` values, labels not tied to inputs. It cannot
see colour contrast, focus order, or whether a modal traps focus. Automated tooling in general
catches roughly **30–40%** of real WCAG issues (axe-core team's own figure) — the rest is manual.

### Linting — use `@html-eslint/eslint-plugin` instead

The plain-HTML equivalent of jsx-a11y. Plugs into the existing flat config in `eslint.config.js`.

```bash
npm i -D @html-eslint/eslint-plugin @html-eslint/parser
```

Useful rules: `require-img-alt`, `require-button-type`, `no-positive-tabindex`,
`require-frame-title`, `require-meta-viewport`, `no-skip-heading-levels`, `require-input-label`,
`no-duplicate-id`, `require-lang`.

### Runtime auditing — where the real value is

| Tool | Command | Notes |
| --- | --- | --- |
| **axe-core CLI** | `npx @axe-core/cli http://localhost:4173` | Best single tool. Exits non-zero on violations, so it gates CI. Run against `npm run preview`. |
| **Lighthouse** | `npx lighthouse http://localhost:4173 --only-categories=accessibility` | Good trackable score, weaker detail than axe. |
| **pa11y-ci** | `npx pa11y-ci http://localhost:4173` | WCAG-ruleset oriented, easy to wire into GitHub Actions. |

### In tests — `vitest-axe`

Vitest + jsdom is already set up, so this drops straight into `tests/`:

```bash
npm i -D vitest-axe
```

```ts
import { axe } from 'vitest-axe'

it('has no detectable a11y violations', async () => {
    expect(await axe(document.body)).toHaveNoViolations()
})
```

Catches regressions on every commit. Caveat: **jsdom has no layout engine**, so contrast,
visibility and focus-order rules will not fire. Still worth having.

### Browser extensions / devtools

- **axe DevTools** (Chrome / Firefox) — the most accurate manual scanner.
- **WAVE** — good visual overlay of landmarks, headings and contrast.
- **Chrome DevTools → Elements → Accessibility pane** — inspect the computed accessibility tree,
  accessible name and role of any element.
- **Chrome DevTools → Lighthouse** — one-click audit.
- **Chrome DevTools → Rendering** — emulate `prefers-reduced-motion` and `prefers-color-scheme`.

## 2. What no tool will tell you

Automation cannot judge intent. These passes are mandatory before calling anything "accessible":

1. **Keyboard-only.** Unplug the mouse. `Tab` / `Shift+Tab` / `Enter` / `Space` / `Esc` / arrows.
   - Can you reach every interactive element?
   - Can you operate every one of them?
   - Is the focus ring _always_ visible?
   - Is the tab order the visual order?
   - Does an open modal trap focus, and does focus return to the trigger on close?
   - Can you escape any component you enter (no keyboard traps)?
2. **Screen reader.** NVDA (Windows, free) or VoiceOver (macOS, `Cmd+F5`).
   - NVDA basics: `Insert+↓` read all, `H` next heading, `D` next landmark, `K` next link,
     `B` next button, `Insert+F7` element list.
   - Does every control announce a meaningful name and role?
   - Does the heading outline make sense read on its own?
3. **200% / 400% zoom** and a 320px viewport width — no content lost, no horizontal scroll.
4. **`prefers-reduced-motion: reduce`** — animations stop or become non-vestibular.
5. **Contrast in context** — over gradients, images and canvas backgrounds, where automated tools
   guess wrong.
6. **Is the alt text actually right?** A linter only checks that the attribute exists.

## 3. Rules to code by

**Semantics first.** A native `<button>`, `<a href>`, `<input>` or `<dialog>` gives you focus,
keyboard behaviour, role and state for free. ARIA is a patch for when no native element fits —
"no ARIA is better than bad ARIA".

**Every control needs an accessible name.** Visible text, `aria-label`, or `aria-labelledby`.
Icon-only and glyph-only buttons (`X`, `☰`) always need one.

**Never remove focus outlines without a replacement.** Style `:focus-visible` with a high-contrast
ring; do not write a bare `outline: none`.

**Keep state in ARIA, not just in CSS classes.** A class like `is-open` is invisible to assistive
tech — pair it with `aria-expanded`, `aria-selected`, `aria-current` or `aria-pressed`.

**Headings are an outline, not a font size.** One `<h1>` per page, no skipped levels. Use CSS for
size.

**Landmarks.** `<header>`, `<nav>`, `<main>` (exactly one), `<footer>`. Label `<section>`s with
`aria-labelledby` pointing at their heading, or they are not exposed as regions.

**Colour is never the only signal.** Pair it with text, an icon or underlining.

**Contrast targets (WCAG 2.2 AA).** 4.5:1 body text, 3:1 for text ≥24px (or ≥19px bold), 3:1 for
UI component boundaries and focus indicators.

**Touch targets** ≥24×24px (AA), 44×44px preferred.

**Decorative visuals get `aria-hidden="true"`** — e.g. the hero `<canvas>`. Never put
`aria-hidden` on anything focusable.

**Respect `prefers-reduced-motion`** for anything moving, parallaxing or auto-playing.

**`<html lang>` must match the content**, and must be updated when the language switcher changes
the copy. Mixed-language fragments get their own `lang` attribute.

**Progressive enhancement.** Content that only exists after JS runs (i18n text) leaves elements
with no accessible name if the script fails. Ship a sensible default in the HTML.

**Skip link.** `<a href="#main" class="skip-link">Skip to content</a>` as the first focusable
element, visible on focus.

**Modals.** `role="dialog"` + `aria-modal="true"` + `aria-labelledby`, focus moved in on open,
focus trapped inside, `Esc` closes, focus restored to the trigger, background content `inert`.
The native `<dialog>` element with `.showModal()` gives most of this for free.

## 4. Suggested npm scripts

```jsonc
{
    "scripts": {
        "lint:a11y": "axe http://localhost:4173 --exit",
        "test:a11y": "vitest run tests/a11y.test.ts"
    }
}
```

Wire `lint:a11y` into CI after a `npm run build` + `npm run preview` step, and add `test:a11y` to
the existing `validate` chain.

## 5. Open items in this project

Findings from the current `index.html` / `src` — tick off as fixed.

- [ ] `index.html:44-50` — language dropdown items are bare `<li data-lang="en">`: not focusable,
      not keyboard-operable, no role. Use a `<button>` inside each `<li>`; give `.lang__switcher`
      `aria-expanded` + `aria-controls`.
- [ ] `index.html:51`, `index.html:146` — buttons labelled with a literal `X`, announced as
      "X button". Add `aria-label="Open menu"` / `aria-label="Close dialog"`.
- [ ] `clickHandler.ts:88` — toggle `aria-expanded` on the nav button alongside the `is-open`
      class.
- [ ] `index.html:142` — contact modal has no `role="dialog"`, `aria-modal="true"` or
      `aria-labelledby`, so it is not announced as a dialog. (Containment, `Esc` close and focus
      restore are already handled: `inert` on header/main/footer at `clickHandler.ts:50-52` and
      `headerContactButton.focus()` at `clickHandler.ts:66`.)
- [ ] `clickHandler.ts:54` — focus is never moved into the modal on open. Because the trigger sits
      inside the now-`inert` header, focus is dropped to `<body>` and Tab restarts from the top of
      the document.
- [ ] `index.html:56-62` — nav links are empty until i18n runs, so they have no accessible name if
      the script fails. Ship the English text as the default.
- [ ] `index.html:72` — `<h2 class="hero-subtitle">` is a subtitle, not a section heading. Make it
      a `<p>`; it currently creates a phantom outline entry.
- [ ] No skip link before the header.
- [ ] No `:focus-visible` styles anywhere in `src/styles` — relying on browser defaults that the
      custom buttons may obscure. Add an explicit high-contrast focus ring.
- [ ] `index.html:3` — `html lang` does not follow the language switch. A genuine WCAG 3.1.1 /
      3.1.2 failure once RU/SR ship.
- [ ] The `#about`, `#skills` and `#projects` sections have no `aria-labelledby` (only `#home`
      does), so they are not exposed as labelled regions.
